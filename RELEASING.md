# Releasing ServicePro

One plan for shipping releases and keeping a changelog. Companion to
[`docs/ops/cloud-run-setup.md`](docs/ops/cloud-run-setup.md) (one-time infra),
[`docs/ops/deploy.md`](docs/ops/deploy.md) (deploy + rollback) and
[`docs/ops/backups.md`](docs/ops/backups.md).

> **Not hosted yet — local only.** The release pipeline is fully wired but
> inert: until the repo variable `GCP_PROJECT_ID` is set, a `v*` tag skips the
> migrate/api/web jobs and **only publishes the GitHub Release notes**. Nothing
> in this document deploys anything until the one-time setup is done.

## TL;DR

Commits pile up on `master` (CI runs, but **nothing deploys**). To ship, **bump
the version and push a `v*` tag**. The tag migrates production, deploys the API
and the web bundle, and publishes the GitHub Release (the changelog). That's a
release.

```bash
make bump                      # edits VERSION (auto-detects the bump)
git add VERSION && git commit -m "release: v0.8.0"
git push origin master
git tag v0.8.0 && git push origin v0.8.0   # -> migrates, deploys, publishes notes
```

## What owns what

- **Changelog = GitHub Releases.** `scripts/gh-release.sh` builds each
  release's notes from the **commit subjects since the previous tag**, filtered
  to user-facing commits. So **good, prefixed commit messages are the
  changelog**. `CHANGELOG.md` is frozen at v0.7.0 (it was generated by
  git-cliff, which is gone).
- **Version number = the root `VERSION` file.** Bumped once per release. The
  pipeline strips the `v` off the tag and passes it as the `APP_VERSION` Docker
  build arg (API) and `VITE_APP_VERSION` (web bundle); the `guard` job has
  already asserted tag == `VERSION`, so there is exactly one number in play.
  The API reports it at `GET /version` → `{"git_sha": "...", "app_version": "..."}`.
  `frontend/package.json`'s `"version"` is not read by the pipeline.

## Commit message contract

The type prefix decides whether a commit appears in the release notes and what
version bump it implies. The `commit-msg` hook (`make install-hooks`) enforces it.

| Prefix                                                                          | Release notes | Bump (pre-1.0)          | Bump (post-1.0) |
| ------------------------------------------------------------------------------- | ------------- | ----------------------- | --------------- |
| `feat:`                                                                         | shown         | MINOR                   | MINOR           |
| `fix:`                                                                          | shown         | PATCH                   | PATCH           |
| `feat!:` / `BREAKING CHANGE`                                                    | shown         | MINOR                   | MAJOR           |
| `deps:`                                                                         | filtered      | PATCH (if nothing else) | PATCH           |
| `chore:` `docs:` `ci:` `build:` `test:` `style:` `refactor:` `perf:` `release:` | filtered      | —                       | —               |

Scopes are fine (`fix(invoices): ...`, `deps(npm): ...`). Reverts of filtered
commits are filtered too; reverting a `feat:`/`fix:` is user-facing and shown.

**Legacy prefixes.** Before v0.8.0 this repo used `minor:` (a feature) and
`major:` (a breaking change). `bump-version.sh` still reads them from history —
`minor:` → MINOR, `major:` → MAJOR (MINOR while 0.x) — and `gh-release.sh`
shows them as user-facing. New commits must use `feat:` / `feat!:`; the hook
rejects `minor:` and `major:`.

```
feat: add recurring job templates
fix(invoices): round tax per line, not per invoice
chore: bump golangci-lint          <- filtered out of release notes
```

## Versioning (SemVer, pre-1.0)

| Bump              | For                            | Example         |
| ----------------- | ------------------------------ | --------------- |
| **PATCH** `0.x.y` | fixes, dependency bumps        | `0.8.0 → 0.8.1` |
| **MINOR** `0.x.0` | features (breaking OK pre-1.0) | `0.8.0 → 0.9.0` |
| **MAJOR** `1.0.0` | GA — only when we leave beta   | —               |

`scripts/bump-version.sh` auto-detects the bump from commit subjects since the
last `vX.Y.Z` tag. In `0.x`, `1.0.0` is never automatic (`--set 1.0.0`).

## Everyday: getting a change in

Work locally, commit with a prefixed message, push to `master` (or open a PR).
Every push and PR runs **CI** (`.github/workflows/ci.yml`): Go lint, unit tests
against Postgres + Redis, govulncheck, OpenAPI drift, frontend
typecheck/lint/tests/dead-code/build/bundle size/npm audit, and a Docker build
of `backend/Dockerfile` with a Trivy scan. CI **deploys nothing**. Keep `master`
releasable — a Dependabot auto-release ships whatever is on it.

If you changed swag annotations, run `make docs` and commit
`backend/docs/` + `frontend/src/types/api.generated.ts`, or the
`openapi-drift` job fails.

## Cutting a release

1. Preview, then bump:
   ```bash
   make bump ARGS="--dry-run"   # show the decision, change nothing
   make bump                    # auto-detect and write VERSION
   make bump ARGS="--set 0.9.0" # force a version (must be strictly higher)
   ```
   It edits `VERSION` only — committing and tagging stay explicit.
2. Commit, push, tag:
   ```bash
   make release-check           # clean tree? prints the tag command
   git add VERSION && git commit -m "release: v0.8.0"
   git push origin master
   git tag v0.8.0 && git push origin v0.8.0
   ```
3. Watch the **Release** run: `guard` → `migrate` → `api` → `web` → `release`.
4. Verify (once hosted):
   ```bash
   curl -s https://servicepro.sharkfins.xyz/version | jq   # through the Worker proxy
   ```

Preview the notes locally without publishing:
`GITHUB_REF_NAME=HEAD scripts/gh-release.sh --dry-run`.

### What the pipeline does, and why in that order

| Job       | Does                                                                                                                   | Why here                                                                         |
| --------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `guard`   | Asserts tag == `VERSION`; decides deploy vs notes-only from `vars.GCP_PROJECT_ID`                                      | A mistyped tag fails in seconds, before a migration touches prod                 |
| `migrate` | `cd backend && go run ./cmd/migrate up` then `version` against `MIGRATION_DATABASE_URL`                                | **Schema first.** Code must never land ahead of its schema                       |
| `api`     | `scripts/deploy-cloudrun.sh`: build → push → deploy `--no-traffic` → shift traffic; then poll `/version`               | The revision must boot and pass its startup probe before it gets traffic         |
| `web`     | Build → Sentry source maps → strip maps → `wrangler deploy` (Worker `servicepro-web`) → verify `/version` via the site | After the API, so the bundle never calls an endpoint that isn't live             |
| `release` | `scripts/gh-release.sh` publishes the GitHub Release                                                                   | Only once the deploy succeeded — or was skipped because hosting isn't configured |

Releases are serialized (`concurrency: release-production`, never cancelled):
aborting a half-finished deploy leaves a migrated database behind the old code.

## Automatic dependency releases

**A merged Dependabot PR cuts a release on its own.**
`dependabot-automerge.yml` merges the PR once CI is green (patch/minor only —
majors wait for review), bumps `VERSION`, commits `release: vX.Y.Z`, dispatches
CI on master and waits for green, then tags and dispatches `release-deploy.yml`
against the tag (a tag pushed with `GITHUB_TOKEN` doesn't trigger workflows on
its own, but `workflow_dispatch` does).

- It ships **everything** unreleased on master, not just the bump.
- `deps:` alone is a PATCH; unreleased `feat:` commits riding along make it a
  MINOR — the version reflects the contents, not the trigger.
- To stop it, comment out the release steps in `dependabot-automerge.yml`.

## Migrations

**Migrations do not run at server startup in production.** They run in the
release `migrate` job, from the CI runner, before the new revision takes
traffic. Locally, docker-compose sets `RUN_MIGRATIONS_ON_STARTUP=true`, and
`make migrate` runs `go run ./cmd/migrate up` against the compose database.

- Migrations live in `backend/migrations/` as numbered golang-migrate pairs
  (`000001_initial_schema.up.sql` is the whole pre-launch schema, squashed 2026-10-24; `make migrate-create NAME=...`
  makes the next pair). Dev seed data is separate: `backend/seeds/dev_seed.sql`
  (`make seed`), never applied in production.
- **Additive only** once production exists. Rename/drop = **two releases**
  (expand, then contract), so the previous revision can still run against the
  migrated schema and a rollback stays safe.
- `MIGRATION_DATABASE_URL` must be a **session pooler / direct** connection
  (port 5432), never a transaction pooler (6543): golang-migrate holds an
  advisory lock across statements. The workflow rejects `:6543`.
- **Pre-applying** a migration out of band: Actions → "DB migrate (manual)" →
  `up` (`.github/workflows/migrate.yml`).

## Background jobs

Production runs no in-process tickers (`RUN_BACKGROUND_WORKERS=false`, set by
`deploy-cloudrun.sh`): Cloud Run throttles CPU between requests and scales to
zero. `.github/workflows/scheduled-jobs.yml` POSTs to
`/internal/jobs/{payment-reminders,analytics-aggregate,webhook-cleanup}` with
`X-Internal-Jobs-Token: $INTERNAL_JOBS_SECRET`. It's a no-op until
`vars.API_URL` is set.

## Rollback

Full runbook: [`docs/ops/deploy.md`](docs/ops/deploy.md). Short version:

- **API** — shift Cloud Run traffic back to the previous revision (revisions
  are named after the tag: `servicepro-api-v0-8-0`):
  ```bash
  gcloud run services update-traffic servicepro-api \
    --region=us-central1 --to-revisions=servicepro-api-v0-7-1=100
  ```
- **Web** — `cd frontend && npx wrangler rollback` (or Workers dashboard →
  servicepro-web → Deployments).
- **Data** — forward-fix with a new migration; never a down-migration in prod.
